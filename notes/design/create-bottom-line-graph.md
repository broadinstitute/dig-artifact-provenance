# `create_bottom_line_graph.py` Design

## Purpose

[create_bottom_line_graph.py](/Users/mduby/Code/DccWorkspace/ArtifactProvenance/src/python/create_bottom_line_graph.py) builds a provenance-oriented dependency graph for the `intake` and `bottom-line` pipelines and writes it to:

- [data/graph/provenance_graph.json](/Users/mduby/Code/DccWorkspace/ArtifactProvenance/data/graph/provenance_graph.json)

The graph is intended to show how data moves:

```text
variants_raw -> variants_processed -> variants -> out/metaanalysis/variants
-> bottom-line ancestry/trans-ethnic outputs
-> min_p / largest derived outputs
-> OpenDataTransferStage published outputs
```

The output JSON has two top-level arrays:

- `nodes`
- `edges`

Each node represents either:

- a pipeline stage
- an S3 data location

Each edge represents a provenance-style dependency between those nodes.

## Primary Inputs

The script consumes local S3 listing snapshots under [data/s3](/Users/mduby/Code/DccWorkspace/ArtifactProvenance/data/s3):

- [dig-anal-variants_processed.txt](/Users/mduby/Code/DccWorkspace/ArtifactProvenance/data/s3/dig-anal-variants_processed.txt)

## Code References

The script uses the public repository:

- `https://github.com/broadinstitute/dig-aggregator-methods`

as the code reference for stage layout and file path conventions.

Stage nodes include a `location_path` pointing to the relevant GitHub source file under that repository.

The generated JSON file contains:

### `nodes`

Each node includes:

- `id`
- `node_type`
- `dapper_class`
- `label`
- `location_path`

Additional fields may include:

- `uri`
- `directory_kind`
- `stage_name`
- `stage_group`

- `dataset`

- `rare`

### `edges`

Each edge includes:

- `id`
- `source`

- `dapper_edge_class`

- `edge_role`

## Provenance Model

The graph uses a simplified DAPPER-inspired model based on [bottom-line-dapper.md](/Users/mduby/Code/DccWorkspace/ArtifactProvenance/notes/gptRecommendations/bottom-line-dapper.md:1).

### Stage nodes

Stage nodes represent pipeline `Activity` objects.

They are annotated with:

- `node_type: "stage"`
- `dapper_class: "Activity"`

Examples:

- `VariantProcessingStage`
- `VariantQCStage`
- `VariantScalingStage`
- `PartitionStage`
- `AncestrySpecificStage`
- `LoadAncestrySpecificStage`
- `TransEthnicStage`
- `LoadTransEthnicStage`
- `MinPStage`
- `MinPTransEthnicStage`
- `LargestStage`
- `OpenDataTransferStage`

### Data nodes

Data nodes represent S3 file or directory artifacts.

They are annotated with one of:

- `dapper_class: "C2M2File"` for raw and intermediate data locations
- `dapper_class: "Dataset"` for logical result locations
- `dapper_class: "DrsObject"` for published open-data outputs

### Edge semantics

Edges use DAPPER-style provenance relationships:

- `Used`
- `WasGeneratedBy`

and `prov:*` predicates, plus `edge_role` where appropriate.

Examples:

- stage uses data input
- dataset was generated by stage
- published output was generated by `OpenDataTransferStage`

## Path Normalization

The S3 listing snapshots include fully qualified S3 URIs, but some include duplicated path prefixes such as:

- `s3://dig-analysis-data/variants/variants/...`
- `s3://dig-analysis-data/out/metaanalysis/bottom-line/out/metaanalysis/bottom-line/...`
- `s3://dig-open-bottom-line-analysis-stg/bottom-line/bottom-line/...`

The script normalizes those to canonical forms before parsing.

Examples:

- `s3://dig-analysis-data/variants/variants/ExChip/...`
  becomes
  `s3://dig-analysis-data/variants/ExChip/...`

- `s3://dig-analysis-data/out/metaanalysis/bottom-line/out/metaanalysis/bottom-line/...`
  becomes
  `s3://dig-analysis-data/out/metaanalysis/bottom-line/...`

- `s3://dig-open-bottom-line-analysis-stg/bottom-line/bottom-line/AA/...`
  becomes
  `s3://dig-open-bottom-line-analysis-stg/bottom-line/AA/...`

This normalization is necessary so the regex-based parsers operate on stable path shapes.

## Parsing Strategy

The script parses the listings into a few logical record types.

### Variant input directories

These come from:

- `variants_raw`
- `variants_processed`
- `variants`

They are parsed as:

- `method`
- `dataset`
- `phenotype`
- `uri`

### Partitioned bottom-line inputs

These come from:

- `out/metaanalysis/variants/<phenotype>/dataset=<dataset>/ancestry=<ancestry>/rare=<true|false>/`

They are parsed as:

- `phenotype`
- `dataset`
- `ancestry`
- `rare`
- `uri`

### Result directories

These come from:

- `out/metaanalysis/bottom-line/...`
- `out/metaanalysis/min_p/...`
- `out/metaanalysis/largest/...`

They are parsed by:

- family
- phenotype
- ancestry for ancestry-specific results
- phenotype only for trans-ethnic results

### Open-data outputs

These come from:

- `s3://dig-open-bottom-line-analysis-stg/bottom-line/<ancestry>/<phenotype>.sumstats.tsv.gz`

They are parsed as:

- `ancestry`
- `phenotype`
- `uri`

## Graph Construction Strategy

The script constructs the graph in three major sections.

### 1. Intake pipeline chain

For each observed `variants/...` location, it creates a chain:

```text
variants_raw -> VariantProcessingStage -> variants_processed
-> VariantQCStage -> variants_qc
-> VariantScalingStage -> variants
```

Notes:

- `variants_qc` is still inferred from code conventions, not directly listed in the current snapshots.
- `variants_raw`, `variants_processed`, and `variants` now come from observed listings where available.

### 2. Bottom-line partitioning and ancestry-specific flow

For each `dataset + phenotype`, the script creates:

```text
variants -> PartitionStage -> out/metaanalysis/variants partitioned directories
```

Then for each `phenotype + ancestry`, it creates ancestry-specific subgraphs:

```text
partitioned variants -> AncestrySpecificStage -> ancestry-specific staging
-> LoadAncestrySpecificStage -> bottom-line ancestry-specific result
```

It also creates corresponding:

- `MinPStage`
- `LargestStage`

branches where observed.

### 3. Trans-ethnic and open-data publication flow

For each trans-ethnic phenotype, it creates:

```text
ancestry-specific bottom-line results -> TransEthnicStage -> trans-ethnic staging
-> LoadTransEthnicStage -> bottom-line trans-ethnic result
```

It also creates:

- `MinPTransEthnicStage`
- trans-ethnic `LargestStage`

where those outputs exist.

Finally, for open-data outputs it creates:

```text
bottom-line result + min_p + optional largest
-> OpenDataTransferStage
-> published .sumstats.tsv.gz endpoint
```

## Node Identity

Node IDs are deterministic and encode node type plus contextual keys.

Examples:

- `stage:PartitionStage__bottom-line__ExChip__ExChip_AFGen__AF`
- `node:variants__ExChip__ExChip_AFGen__AF`
- `node:bottom_line_ancestry_specific__bottom-line__Acne__EU`
- `node:open_data_endpoint__Acne__EU`

This lets the script merge repeated references to the same location or stage instance without duplication.

## `location_path`

Every node now includes `location_path`.

### For data nodes

`location_path` is the normalized S3 URI.

Examples:

- `s3://dig-analysis-data/variants_raw/ExChip/ExChip_AFGen/AF/`
- `s3://dig-analysis-data/out/metaanalysis/bottom-line/ancestry-specific/Acne/ancestry=EU/`
- `s3://dig-open-bottom-line-analysis-stg/bottom-line/AA/Acne.sumstats.tsv.gz`

### For stage nodes

`location_path` is a GitHub `blob` URL to the corresponding pipeline source file in:

- `https://github.com/broadinstitute/dig-aggregator-methods`

Examples:

- `.../intake/src/main/scala/VariantProcessingStage.scala`
- `.../bottom-line/src/main/scala/PartitionStage.scala`
- `.../bottom-line/src/main/scala/OpenDataTransferStage.scala`

## Observed Versus Inferred Nodes

The script distinguishes between:

- `observed_from_listing: true`
- `observed_from_listing: false`

Observed nodes come directly from S3 listings.

Inferred nodes come from path conventions in the intake or bottom-line code and include:

- `inferred_from_code`

This is especially important for:

- `variants_qc`
- `bottom-line` staging directories

which are not represented in the current listing snapshots but are required to express the pipeline flow.

## Missing Listing Handling

The script checks for the required listing files before graph construction.

If a required listing is missing, it reports:

- the expected local file
- the bucket/prefix it represents

As of Friday, August 21, 2026, the updated snapshot set covers all required buckets used by the script, so graph generation should succeed without missing-listing warnings.

## Current Limitations

### `variants_qc` is inferred

There is no current listing snapshot for:

- `s3://dig-analysis-data/variants_qc/`

So `variants_qc` nodes are inferred from the intake code path convention.

### Stage internals are simplified

The graph models the main stage-to-artifact dependencies but does not attempt to represent:

- individual Spark part files
- per-file manifests inside each directory
- every shell helper or bootstrap action
- row-level or variant-level lineage

### Open-data endpoints are file nodes only

The open-data listing is represented at the `.sumstats.tsv.gz` object level, not as a richer package manifest.

## Execution

Run the script from the repository root:

```bash
python3 src/python/create_bottom_line_graph.py
```

It writes:

- [provenance_graph.json](/Users/mduby/Code/DccWorkspace/ArtifactProvenance/data/graph/provenance_graph.json)

and prints:

- the number of nodes
- the number of edges
- any missing listing warnings

## Intended Use

This script is designed to support:

- provenance inspection
- graph export for downstream DAPPER mapping
- identifying which intake and bottom-line stages contribute to published open-data outputs
- future generation of more formal provenance documents

It is not a general-purpose S3 crawler. It is a pipeline-specific graph builder grounded in:

- observed listing snapshots
- known code path conventions
- DAPPER-oriented provenance semantics
